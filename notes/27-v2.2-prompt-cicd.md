# 27 — v2.2 Prompt CI/CD (golden suites + judge + GitHub Action)

> The feature that makes Loupe a different category from LangFuse/LangSmith/Helicone.
> Not "another observability tool" but **replay-driven prompt testing**: a prompt PR
> runs a regression suite against saved production traces, a judge LLM scores each
> replay, and a red check blocks the merge.

---

## What it is (in one breath)

A prompt is code, but it fails **silently** and **non-deterministically** — break it and
no test fails, the app just gives wrong answers until a user complains. v2.2 gives a prompt
the same green/red safety net real code has: take ~15 real production traces as a **golden
suite**, replay each against the new prompt, have an **LLM judge** score old-vs-new as
`equivalent / improved / regressed`, and **block the PR on any regression**.

The whole loop reuses machinery that already existed: the **v2.1 replay engine** (re-run a
trace with a new prompt) and the **diff view** (see original vs new). v2.2 = "replay *many* +
auto-judge + wrap in GitHub."

Full plain-language rationale + examples: [docs/concepts-explained.md](../docs/concepts-explained.md).
Every design decision: [ARCHITECTURE_DECISIONS.md](../ARCHITECTURE_DECISIONS.md) B8.1–B8.5.

## The design, locked before any code (B8.1–B8.5)

We settled five decisions first (the project's habit — argue the "why" before building):

- **B8.1 — suite storage by reference.** A suite is a named *set of trace IDs* via a
  `suite_traces` join table, not copies. Traces are immutable, so a snapshot buys nothing.
- **B8.2 — `suite_runs.results` JSONB.** A run is read as a whole (PR comment, one page), so
  per-trace verdicts live in one JSONB column, not a child table.
- **B8.3 — global rubric + per-suite override.** Zero-config default; a suite can supply
  stricter criteria. The shared default prompt-caches across judgments.
- **B8.4 — hybrid scoring, pluggable judge.** Deterministic check first (free), LLM judge only
  on the free-text answer. Backend is pluggable: **free Groq/Llama by default**, Claude opt-in.
- **B8.5 — composite Action, zero-tolerance gate.** The Action wraps the CLI; any regression
  blocks (no confidence gating — an unreliable number shouldn't gate the decision).

## Sub-step 1 — DB layer

Three tables ([models.py](../server/app/models.py), migration `e5b2d9c4a7f1`):
`suites` (name + optional `judge_rubric`), `suite_traces` (join, composite PK, cascade),
`suite_runs` (status + counts + `results` JSONB + `judge_backend`).

**Why a join table over a JSONB array of IDs:** FK integrity (no dangling `trace_id`) and a
free reverse query ("which suites use this trace?") via an index — a JSONB array loses both.

**Testing habit that paid off:** verified the migration **round-trips** (upgrade → downgrade →
re-upgrade). A one-directional migration that can't roll back is a production trap.

---

## Sub-step 2 — JudgeService

Two stages ([judge.py](../server/app/services/judge.py)):

1. **Deterministic pre-check (free).** Canonicalise both outputs (JSON, sorted keys); if
   identical → `equivalent`, **no LLM call**. This nips the common "the prompt change didn't
   affect this trace" case for $0.
2. **LLM judge (only on a difference).** One call → guaranteed-valid
   `{label, reasoning, confidence}` scored against the rubric.

**Pluggable backend** (`"<provider>/<model>"`): `groq/...` (free default, JSON mode) or
`claude/...` (opt-in, `output_config.format` for schema-valid JSON — the claude-api skill's
recommended structured-output path).

**Why not a numeric similarity score?** Embeddings give *similarity*, not *direction* —
"82% similar" doesn't say better-or-worse. The judge returns a **directional** verdict, which
is the whole point (a regex/embedding can't).

**The cost-proving test:** `mock_call.assert_not_awaited()` on identical outputs — proof the
deterministic path actually skips the LLM. Small check, big cost impact (the free-tier daily
token budget lasts 2–3× longer because most traces never hit the judge).

## Sub-step 3 — endpoints

`POST /v1/suites` (validates trace ownership), `GET /v1/suites[/{id}]`,
`POST /v1/suites/{id}/run` (**202 + run_id**, async), `GET /v1/suite_runs/{id}` (poll)
([suites.py](../server/app/routers/suites.py)).

**Why async (A5, not a cron).** The run is event-driven (fired by the PR), but a 100-trace run
= 100 replays + up to 100 judge calls = minutes — which can't fit in one HTTP request without
timing out. So the endpoint returns `202 Accepted` + a `run_id` and hands the work to a
**BackgroundTask**; the caller polls. `_run_suite` reuses `_run_replay` per trace, then judges.

**Resilience:** each trace is in its own `try/except` — one bad trace bumps `errored` and moves
on; it never kills the whole run (a single flaky trace shouldn't block a whole PR).

---

## Sub-step 4 — CLI

`loupe suite create/run/diff` ([cli.py](../sdk/loupe/cli.py)) — thin HTTP over the endpoints.

- `create --from last:N` (excludes replays — golden suites are production traces) and/or
  `--trace <id>`.
- `run <id> --prompt file` — POST the new prompt, poll the async run, print a pass/regress
  summary with diff links, and **exit non-zero on any regression**.
- `diff <a> <b>` — side-by-side counts + per-trace verdict changes.

**The one line that powers the whole GitHub gate:**
```python
raise SystemExit(1 if run["regressed"] else 0)
```
Regression → non-zero exit → CI step fails → red check → merge blocked. The Action needs no
new logic because the CLI already did call + poll + summary + exit code.

---

## Sub-step 5 — GitHub Action + demo

**Composite** action ([loupe-action/action.yml](../loupe-action/action.yml)): setup Python →
`pip install loupe-sdk` → `loupe suite run` → `gh pr comment` → `exit <cli code>`. That's it.

**Why composite, not a TypeScript action:** the CLI is the engine; a TS action would
re-implement it. One engine, two entry points (human CLI + CI). The "I avoided duplication"
story is stronger than "I wrote a TS action."

Demo ([examples/prompt-ci-demo/](../examples/prompt-ci-demo/)): a prompt file + a *template*
workflow (kept out of `.github/` so it doesn't run on this monorepo without secrets) + a
killer-flow runbook. Reachability caveat documented honestly: GitHub-hosted runners can't
reach `localhost`, so a live demo points at the deployed Render instance; free Groq judge +
a ~15-trace suite keeps a run ~$0.

## Interview Q&A

**Q: How is "regressed" determined — is it a rule?**
No. The replayed output is compared to the original by an **LLM judge against an explicit
rubric** (correctness, usability, completeness). Identical outputs short-circuit to
`equivalent` for free; differences get a directional verdict with reasoning. That's why it
catches semantic breakage a regex can't — e.g. valid-but-wrong-shape output.

**Q: Why default the judge to a free model?**
The judge backend is pluggable; the default is free Groq/Llama so the whole loop is $0 to
self-host and demo, with Claude as an opt-in quality upgrade. A 100-trace run is <$1 on Claude
anyway — cost isn't the constraint, verdict reliability is. "Zero-cost to self-host, Claude for
production" is a deliberate accessibility choice.

**Q: Why zero-tolerance instead of a pass-rate threshold or confidence gate?**
Any regression blocks. I don't gate on the judge's self-reported confidence — it's an
unreliable number, and gating a shaky signal on another shaky signal adds noise, not safety.
Confidence is stored for human review only. A `--max-regressions N` knob is left as future
loosening for large suites.

**Q: Why is the run async if it's triggered synchronously by the PR?**
Event-driven trigger, background execution. 100 traces × (replay + judge) = minutes, which
would time out a synchronous HTTP request. The endpoint returns a `run_id` immediately and the
Action polls — the A5 (BackgroundTasks) decision at suite scale.

**Q: How does this differ from LangSmith/Helicone?**
They observe. Loupe closes a loop: production trace → saved as a test → run on every prompt PR →
block bad merges. Helicone can't even do it — it doesn't run your agent graph. Loupe's SDK is
both the instrumentation *and* the execution engine, so it owns capture, replay, and the gate.
